## Context

The idea says "required in CI", but the acceptance criterion only said "executes successfully". The `swift` job runs on an expensive macOS runner and is gated by change detection, and no UI-test target exists yet.

## Alternatives

1. Keep the test in the repository and record dated local runs only
2. Run it in CI as informational, not merge-blocking

## Decision

Run the first-garden UI test on a simulator in the existing `swift` job, under that job's change-detection filter, so it is part of "All gates".

## Reason

This matches the idea's "required in CI", and the existing narrow Swift filter limits the runner cost.

## Consequences

The macOS job takes longer on iOS PRs. Flaky simulator UI tests will block merge of iOS changes. The test does not run on PRs that do not touch the Swift filter paths.
